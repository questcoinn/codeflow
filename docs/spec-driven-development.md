## SDD의 문제점

스펙 중심 개발(Spec-Driven Development, SDD), 특히 AI 어시스턴트나 자율 코딩 에이전트를 활용하는 환경에서의 SDD는 운영 방식에 따라 기획과 실제 코드 간의 괴리, 관리 오버헤드, 시스템의 유연성 저하라는 위험을 가집니다. 아래 문제들은 SDD 자체의 숙명이라기보다, 스펙의 범위와 운영 규칙을 잘못 잡았을 때 나타나는 실패 패턴입니다.

> 특정 도구(OpenSpec)에 이 내용을 적용하는 방법은 [openspec-practices.md](openspec-practices.md)에 따로 정리했습니다.

1. 스펙 범위를 크게 잡으면 '워터폴(Waterfall)'이 된다

시스템 전체의 기술 명세를 코드 작성 전에 한 번에 정의하려 하면, 과거의 폭포수(Waterfall) 모델과 같은 오류를 범하게 됩니다. 프로젝트에 대해 가장 무지한 기획 초기 단계에 크고 경직된 아키텍처 결정을 내리게 되고, 개발 중 마주치는 기술적 변수에 유연하게 대처하지 못해 오버엔지니어링으로 이어지기 쉽습니다.

> 참고: 최신 SDD 도구 중에는 변경 단위로 바뀌는 부분(delta)만 작성하는 점진적 방식을 취하는 것도 있습니다. 이런 도구를 쓰더라도 하나의 변경에 너무 많은 범위를 담으면 이 문제는 똑같이 나타납니다.

2. 자연어의 본질적인 모호성

스펙을 작성하는 자연어(기획서, 프롬프트 등)는 본질적으로 모호합니다. AI 에이전트가 오해 없이 코드를 짜도록 모호성을 완전히 제거하려면, 스펙 자체를 거의 프로그래밍 언어에 준하는 수준으로 장황하고 치밀하게 작성해야 합니다. 결과적으로 '코딩을 안 하려고 스펙을 쓰는데, 스펙을 쓰는 행위가 코딩만큼 고통스러워지는' 모순이 발생합니다.

3. 상류(Upstream) 변화에 따른 취약성과 토큰 낭비

비즈니스 요구사항이나 데이터베이스, 배포 환경 같은 상류 의존성이 바뀌면, 하나로 뭉쳐진 큰 기술 명세는 광범위한 수정이 필요해집니다. 스펙 경계가 나뉘어 있지 않으면 백엔드 로직, 큐 시스템, 인프라 변경 사항을 AI 에이전트에게 다시 이해시키기 위해 많은 양의 컨텍스트(토큰)를 반복해서 소모하는 경제적·시간적 비용이 발생합니다.

4. 스펙 드리프트(Specification Drift)와 진실의 원천 분열

코드와 스펙이 분리되어 있으면, 코드가 수정되는 속도를 스펙 문서가 따라가지 못하는 '스펙 드리프트'가 일어나기 쉽습니다. 특히 핫픽스나 급한 수정처럼 스펙 절차를 건너뛰고 코드를 직접 고치는 경로가 드리프트의 주된 원인입니다. 시스템의 실제 상태를 보여주는 '진실의 원천(Source of Truth)'이 코드와 스펙 두 군데로 쪼개지면, 낡은 명세를 바탕으로 AI가 엉뚱한 코드를 재생산하는 악순환이 생깁니다.

5. 부실한 요구사항의 고속 대량 복제

SDD는 부실하거나 모호한 요구사항을 해결해 주지 못합니다. 오히려 잘못된 방향을 더 빠르게 실행할 뿐입니다. 기획이나 프롬프트에 숨어 있던 논리적 오류나 검증되지 않은 가정을 AI가 정교한 구조의 코드로 빠르게 대량 생산하기 때문에, 나중에 잘못된 부분을 찾아내 뒤엎는 비용이 더 커집니다. 이는 SDD만의 문제가 아니라 AI 코딩 전반의 문제이지만, 스펙이 '검증된 문서'처럼 보이는 탓에 SDD에서 더 쉽게 간과됩니다.

6. 검토(Review) 및 검증의 병목 현상

하나의 스펙을 기반으로 데이터베이스 스키마부터 프런트엔드 컴포넌트까지 한 번에 생성되면, 인간 개발자가 검토해야 할 코드 양이 감당하기 어려울 정도로 늘어납니다. 근본 원인은 한 번에 만들어지는 변경의 크기입니다. 큰 코드 블록의 아키텍처적 결함을 뒤늦게 발견하면 개발 속도가 급격히 꺾이는 '가속도 멀미' 현상을 겪게 되며, 보이지 않는 기술 부채와 프로덕션 결함이 숨어들 확률이 높아집니다.

## 방안

위 한계들을 줄이고, AI 에이전트와 인간 개발자가 안전하게 협업하기 위한 구체적인 방안을 제안합니다. 각 방안은 문제를 '완전히 제거'하기보다 위험을 관리 가능한 수준으로 낮추는 것을 목표로 합니다.

1. '워터폴' 문제: Tracer Bullet(예제 관통) 아키텍처

- 해결책: 전체 아키텍처를 한 번에 설계하지 말고, 가장 핵심이 되는 기능 하나만 프런트엔드부터 데이터베이스까지 관통하는 최소한의 코드(Tracer Bullet)를 먼저 작성합니다. 이것을 첫 번째 스펙 변경으로 진행합니다.
- 효과: 기술적 불확실성을 초기 단계에 마주하고 해결할 수 있어, 프로젝트 후반부에 스펙을 통째로 갈아엎을 위험을 줄입니다. 스펙은 이후 변경을 거치며 점진적으로 구체화됩니다.

2. '자연어 모호성' 문제: 의도·동작·구조를 나눠서 명세

- 해결책: 구현 방법을 자연어로 구구절절 설명하지 않고, 명세를 세 층으로 나눕니다.
  - 의도(Why/What): 인간은 비즈니스 의도와 범위 밖인 것만 짧게 적습니다.
  - 동작(Behavior): 에러 처리, 처리 순서, 경계값 같은 동작은 요구사항과 GIVEN/WHEN/THEN 시나리오 형식으로 구체적인 사례로 적습니다.
  - 구조(Structure): 데이터 구조와 인터페이스는 JSON Schema, OpenAPI, Protobuf 같은 엄격한 규격으로 정의합니다.
- 효과: 스키마는 구조의 모호성을, 시나리오는 동작의 모호성을 줄여 AI 에이전트의 해석 오류를 줄입니다. 스키마만으로는 동작의 의미를 담을 수 없으므로 두 가지를 함께 씁니다.

3. '토큰 낭비와 변경 취약성' 문제: 기능(Capability) 단위 스펙 경계

- 해결책: 시스템 전체를 하나의 스펙으로 묶지 말고, 스펙을 기능(capability) 단위로 나눠 관리합니다. 이것은 AI에게 줄 컨텍스트를 나누는 것이지, 배포 단위를 마이크로서비스로 쪼개는 것이 아닙니다. DB 스키마, 인프라, 외부 API처럼 여러 기능이 함께 의존하는 상류 요소는 별도의 공용 계약(contract) 스펙 하나에 모아 둡니다.
- 효과: 상류가 바뀌면 공용 계약 스펙과 그에 의존하는 기능 스펙만 다시 읽히면 되므로, 전체 스펙을 다시 넣는 것보다 토큰 비용과 컨텍스트 오염이 줄어듭니다. 상류 변경은 본래 여러 기능에 걸쳐 영향을 주므로, 영향 범위를 0으로 만드는 것이 아니라 추적 가능하게 만드는 것이 목표입니다.

4. '스펙 드리프트' 문제: Spec-as-Code와 드리프트 감지

- 해결책: 스펙 문서를 Notion이나 Confluence 같은 외부 위키에 두지 않고, 소스코드 저장소(Git) 안에서 코드와 함께 관리합니다. 그리고 "스펙을 먼저 바꾸고 코드를 바꾼다"는 순서를 지킵니다.
  - CI는 스펙을 직접 고치지 않습니다. 코드 변경이 스펙과 어긋나는지 **감지해서 경고만** 하고, 스펙에 반영할지는 사람이 결정·승인합니다.
  - 핫픽스처럼 스펙 절차를 건너뛴 변경은 사후에 반드시 스펙 변경으로 기록하도록 규칙을 둡니다.
- 주의: 코드가 바뀔 때마다 LLM이 스펙을 자동으로 역갱신하게 만들면, 코드가 진실의 원천이 되고 스펙은 '코드가 지금 하는 일'을 받아 적은 문서로 전락합니다. 코드에 있는 버그까지 정상 동작으로 스펙에 기록되므로 피해야 합니다.
- 효과: 스펙과 코드가 같은 버전으로 묶여 움직이고, 어긋나는 순간이 드러나므로 AI가 낡은 문서를 보고 코드를 짤 위험이 줄어듭니다.

5. '부실한 요구사항 복제' 문제: 스펙 검증 루프(Pre-Flight Check)

- 해결책: 인간이 작성한 스펙을 코딩 에이전트에게 바로 넘기지 않고, 두 단계로 검증합니다.
  - 스펙 검증 에이전트(Specification Critic): "누락된 예외 처리는 무엇인가?", "논리적 모순이 있는가?"를 먼저 묻게 합니다. 가능하면 스펙을 쓴 것과 다른 모델이나 다른 프롬프트를 사용해 같은 맹점을 공유하지 않게 합니다.
  - 사람·도메인 검증: "이 요구사항이 애초에 맞는가?"는 LLM이 판단할 수 없으므로, 사용자나 도메인 담당자의 확인 또는 Tracer Bullet 수준의 프로토타입으로 검증합니다.
- 효과: 누락된 예외와 논리 모순은 코드로 복제되기 전에 스펙 단계에서 걸러지고, 잘못된 가정은 사람의 확인을 거치면서 줄어듭니다.

6. '검토 병목' 문제: 변경 크기 제한과 테스트 우선

- 해결책:
  - 변경 크기 제한: 변경 하나당 작업 수나 diff 크기에 상한을 둡니다. 리뷰 병목에 가장 직접적인 대책입니다.
  - 테스트 우선(Test-Driven Prompting): AI에게 구현보다 테스트 코드나 인터페이스 정의를 먼저 작성하게 하고, 생성된 코드가 테스트를 통과하는지 CI에서 자동으로 검증합니다.
  - 테스트 자체의 검증: AI가 쓴 테스트는 항상 통과하도록 만든 의미 없는 테스트가 되기 쉬우므로, 사람이 테스트를 리뷰하고 뮤테이션 테스트나 속성 기반 테스트로 보완합니다.
- 효과: 리뷰어는 모든 구현 코드를 줄 단위로 읽는 대신 테스트와 비즈니스 로직의 흐름에 집중할 수 있어 검토 부담이 줄어듭니다. 단, 테스트로는 아키텍처 결함을 잡을 수 없으므로 설계(design) 단계 리뷰는 별도로 유지합니다.

## 적용 범위

SDD 절차는 모든 작업에 필요하지 않습니다. 다음 경우는 SDD 없이 바로 처리합니다.

- 동작 변경이 없는 작은 버그 수정, 오타 수정, 리팩터링
- 일회성 스크립트, 실험용 코드
- 의존성 버전 업데이트처럼 외부에서 관찰되는 동작이 바뀌지 않는 작업

반대로 외부에서 관찰되는 동작, 인터페이스, 데이터 구조가 바뀌는 작업은 스펙 변경을 거쳐 진행합니다.

## 문서가 늘어날 때의 문제

스펙 문서를 코드와 함께 git으로 관리하면 시간이 갈수록 문서가 늘어납니다. 이때 생기는 걱정은 두 가지입니다. 스펙 충돌을 감지하기 어려워지는 것, 그리고 문서가 코드보다 많아지는 것입니다. 두 문제는 서로 다른 종류의 문서에서 생기므로 나눠서 봐야 합니다.

| 문서 종류 | 무엇에 비례해 늘어나나 | 다시 읽히나 |
|---|---|---|
| 현재 스펙 (지금 시스템이 어떻게 동작하는가) | 기능(capability) 수. 변경이 병합되므로 기능 하나당 스펙은 하나 | 자주 읽힘. 지금 동작의 기준 |
| 변경 기록 (완료된 제안서·설계·작업 목록) | 변경 수. 변경 하나당 문서 여러 개가 계속 쌓임 | 거의 안 읽힘 |

파일 개수가 늘어나는 곳은 변경 기록이고, 스펙 충돌이 문제 되는 곳은 현재 스펙입니다.

### 스펙 충돌 감지

- 두 변경이 같은 요구사항을 고치면 병합할 때 git이 텍스트 충돌로 잡아 줍니다. 이쪽은 쉬운 문제입니다.
- 어려운 것은 **의미 충돌**입니다. 서로 다른 스펙 파일에 있는 두 요구사항이 모순되는 경우입니다(예: auth 스펙의 "세션은 30분 후 만료"와 다른 스펙의 "로그인 상태 7일 유지"). git도, 문서 형식만 검사하는 검증 도구도 잡지 못합니다.

대책 (위쪽일수록 효과가 큼):

1. **규칙 하나는 한 곳에만 둡니다.** 다른 스펙에 이미 있는 규칙은 복사하지 않고 참조합니다. 여러 기능이 같이 쓰는 규칙은 공용 계약 스펙에 모읍니다(방안 3). 의미 충돌은 대부분 중복에서 생깁니다.
2. **시나리오를 테스트로 연결합니다.** 모순되는 두 요구사항은 문서 리뷰로는 놓쳐도 테스트에서는 실패로 드러납니다. 지금 가장 믿을 만한 감지 수단입니다.
3. **새 변경을 제안할 때 관련 스펙을 먼저 찾습니다.** 새 변경이 기존 요구사항과 겹치거나 모순되면 제안서에 명시합니다.
4. **현재 스펙 전체를 주기적으로 점검합니다.** 스펙 검증 에이전트(방안 5)를 새 변경뿐 아니라 현재 스펙 전체에 돌립니다. LLM 점검이라 놓치는 것이 있을 수 있습니다.

완전한 해결책은 없습니다. 목표는 충돌이 생길 자리를 줄이고, 생기면 빨리 드러나게 하는 것입니다.

### 문서가 코드보다 많아지는 문제

파일 개수 자체는 좋은 지표가 아닙니다. 비용은 계속 고쳐야 하는 문서와 읽어야 하는 문서에서 생깁니다.

- **변경 기록**: 한 번 쓰면 고치지 않으므로 관리 비용은 거의 없습니다. 실제 비용은 검색 결과가 지저분해지는 것, 그리고 에이전트가 오래된 설계 문서를 현재 결정으로 착각하고 참고할 위험입니다. 검색과 에이전트 컨텍스트에서 변경 기록을 제외합니다(`.ignore` 등). 너무 많아지면 오래된 기록을 지우는 것도 방법입니다. git 이력에서 복원할 수 있습니다.
- **현재 스펙이 코드만큼 커진다면**: 개수 문제가 아니라 스펙에 구현 세부사항이 들어갔다는 신호입니다. "구현을 바꿔도 외부 동작이 바뀌지 않는다면 스펙에 넣을 내용이 아니다"라는 기준으로 걸러냅니다. 문제점 1(워터폴)이 문서 크기로 드러나는 것입니다.
- **변경 크기 조절**: 작은 수정까지 모두 스펙 변경으로 만들면 변경 기록이 빠르게 늘어납니다. 동작이 바뀌지 않는 작업은 스펙 절차 없이 처리하고(적용 범위 참고), 설계 문서는 아키텍처 변경, 새 의존성, 보안·마이그레이션 이슈처럼 설계 판단이 필요할 때만 씁니다. 반대로 변경을 너무 크게 만들면 리뷰 병목(문제점 6)이 생기므로 균형이 필요합니다.

요약하면, 현재 스펙은 시스템 크기를 따라 커져야 하고 그보다 빨리 커지면 설계 문서로 변하고 있다는 경고입니다. 변경 기록은 쌓여도 괜찮지만 검색과 에이전트가 참고하는 범위에서는 뺍니다.
