# 테스트 코드 작성

좋은 테스트는 실패했을 때 무엇이 깨졌는지 바로 알려 주고, 처음 보는 사람도 그 파일 하나만 읽고 이해할 수 있다. 테스트는 사람이 읽고 유지하는 코드다. 개수나 커버리지를 늘리려고 쓰지 않는다.

## 작업 순서

### 1. 프로젝트 관례 파악

- 기존 테스트를 몇 개 읽고 프레임워크, 파일 위치, 이름 규칙, 실행 명령을 확인한다. 프로젝트 관례가 이 문서의 일반 예시보다 우선한다.
- 이미 있는 헬퍼와 fixture는 재사용한다.
- 테스트 환경이 없으면 언어의 표준 도구를 우선 쓴다. 새 의존성을 추가해야 한다면 사용자에게 먼저 확인한다.

### 2. 스펙 찾기

스펙을 볼 수 있으면 레퍼런스로 삼는다. 코드는 "지금 하는 일"만 보여 주고, 스펙은 "해야 하는 일"을 알려 준다. 코드만 보고 쓴 테스트는 버그까지 정상 동작으로 고정할 수 있다.

- 사용자가 알려 준 문서, `openspec/specs/`, `specs/`, `docs/`, README, 이슈나 PR 설명 순서로 찾는다. 오래 찾지 말고, 없으면 공개 인터페이스와 호출부에서 의도를 읽는다.
- 코드와 스펙이 다르면 테스트를 어느 한쪽에 조용히 맞추지 않는다. 어떤 차이인지 보고한다. 스펙이 맞다고 판단되면 스펙대로 테스트를 쓰고, 실패하는 테스트로 남겨 사용자가 결정하게 한다. 소스 코드는 요청이 없으면 고치지 않는다.

### 3. 무엇을 테스트할지 고르기

스펙 항목을 하나씩 테스트로 옮기지 않는다. 테스트는 모두 유지 비용이 들기 때문에, 그 비용보다 막아 주는 위험이 큰 것만 쓴다.

**쓴다** (아래 질문에 "그렇다"가 많을수록 우선):
- 깨지면 금전 손실, 데이터 손상, 보안 문제, 사용자에게 보이는 장애로 이어지는가?
- 핵심 비즈니스 규칙인가? 분기나 경계값이 있어 틀리기 쉬운가?
- 호출자가 의존하는 공개 계약인가? 예전에 버그가 났던 곳인가?

**쓰지 않는다**:
- 타입 시스템, 컴파일러, 프레임워크가 이미 보장하는 것
- 상수 값, 단순 getter/setter, 로그 문구처럼 그대로 옮겨 적기만 하는 검증
- 라이브러리 자체의 동작
- 다른 테스트가 이미 같은 이유로 잡아 주는 경우
- 내부 구현 방식. 리팩터링만 해도 깨지는 테스트는 동작을 보호하지 못한다

### 4. 명료하게 작성

읽는 사람의 비용을 줄이는 것이 DRY보다 우선한다. 테스트 사이에 코드가 조금 반복돼도, 각 테스트가 혼자 읽히는 쪽을 택한다.

- **테스트 하나에 동작 하나.** 이름이 조건과 기대 결과를 문장처럼 말하게 한다. 실패했을 때 이름만 보고 무엇이 깨졌는지 알 수 있어야 한다.
- **위에서 아래로 읽힌다.** 준비, 실행, 검증이 순서대로 드러나고, 다른 곳을 찾아가지 않아도 이해된다.
- **기대값은 리터럴로 적는다.** 테스트 안에서 기대값을 계산하면 구현을 복사하게 되고, 같은 버그를 함께 갖게 된다.
- **테스트에 분기와 반복을 넣지 않는다.** 테스트 본문의 `for`도, 테스트를 만들어 내는 `for`도 읽는 사람이 머릿속으로 실행해야 한다. 입력만 다른 경우가 두세 개면 테스트를 나눠 각각 이름을 준다. 그보다 많을 때만 프레임워크의 표 기반 기능(`parametrize`, `test.each`, Go의 table test, `unittest`의 `subTest`)을 쓴다.
- **공개 인터페이스로 검증한다.** 내부 필드나 컬렉션을 들여다보지 않는다. 오류 메시지 문구나 결과 순서도 계약으로 약속된 경우에만 확인한다. 약속되지 않은 것을 고정하면 동작이 그대로여도 테스트가 깨진다.
- **입력에는 이 테스트와 관련된 값만 드러낸다.** 값이 왜 그 값인지 보이게 하고, 의미 없는 값으로 눈을 분산시키지 않는다.
- **mock은 경계에만 쓴다.** 네트워크, 시간, 난수, 파일 시스템처럼 통제가 안 되는 곳만 대체한다. 내부 함수 호출 횟수가 아니라 결과를 검증한다.
- **주석은 코드로 드러나지 않는 이유만 적는다.**

```python
# 피한다: 이름이 동작을 말하지 않고, 기대값을 구현처럼 계산하고, 무엇이 핵심인지 안 보인다
def test_discount():
    order = make_order()
    assert apply_discount(order).total == order.total - order.total * RATE

# 좋다: 이름, 입력, 기대값만으로 규칙이 읽힌다
def test_orders_of_100000_or_more_get_10_percent_off():
    order = Order(total=100_000)
    assert apply_discount(order).total == 90_000
```

### 5. 테스트 헬퍼는 마지막 수단

헬퍼는 읽는 사람을 다른 파일로 보내고, 그 자체도 유지보수 대상이 된다. 기본값은 "만들지 않는다"다.

먼저 인라인으로 써 본다. 다음이 **모두** 맞을 때만 만든다.
- 같은 준비 코드가 여러 테스트에 반복되고, 그 길이가 테스트의 의도를 실제로 가린다
- 이름만 보고 무엇을 하는지 알 수 있다
- 프레임워크 기능(fixture 등)으로는 더 단순하게 풀리지 않는다

만들 때는 최소 한도로 둔다.
- 객체 준비 같은 단순한 일만 맡긴다. 검증을 숨기거나, 분기와 옵션이 많은 작은 프레임워크로 키우지 않는다.
- 테스트에서 중요한 값은 헬퍼 안에 숨기지 않고 인자로 넘겨 테스트에 드러낸다.
- 한 파일에서만 쓰면 그 테스트 파일 안에 둔다. 여러 파일에서 쓸 때만 테스트 디렉터리 안의 지원 파일로 뺀다.
- **소스 코드와 분리한다.** 프로덕션 코드 경로에 두지 않고, 프로덕션 코드가 import하지 않으며, 빌드 산출물에 포함되지 않게 한다. 언어 관례(Go의 `_test.go`, Rust의 `#[cfg(test)]` 등)가 있으면 따른다.
- 테스트만을 위해 프로덕션 코드에 export, 플래그, 분기를 추가하지 않는다. 필요해 보이면 사용자에게 알린다.

### 6. 실행하고 확인

- 작성한 테스트를 실제로 실행한다. 실행할 수 없으면 그 사실과 이유를 보고한다.
- 통과만으로는 부족하다. 항상 통과하는 테스트는 안전하다는 착각만 준다. 핵심 테스트 몇 개는 구현을 일부러 바꿔 실제로 실패하는지 확인한다. 실제 소스 대신 새로 만든 고유한 임시 폴더의 복사본에서 하고, 끝나면 그 폴더를 지운다.
- 테스트가 실패하면 원인을 본다. 버그를 찾았다면 테스트를 통과하도록 약하게 고치지 않고 보고한다.
